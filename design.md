# Thanos — design

This document describes the intended architecture of the Thanos
codebase after the 2026-08-05 consolidation pass, the reasoning behind
it, and the redundancies that pass removed. It is the reference for
"where does this belong?" when extending the code.

## Design philosophy

1. **A pure core, a thin reactive shell.** Everything that computes —
   masks, binning, counting, SQL generation, plotting from counts — is
   a plain function testable from a script. Shiny reactivity is
   confined to `thanosServer()`, which only *wires* pure pieces
   together. This is why the test suite can prove behavior without a
   browser.
2. **Backends are data contracts, not classes.** A backend is a named
   list of functions (documented in `R/thanos_backend.R`). The module
   consumes the contract and never knows whether data lives in a data
   frame, SQLite, or DuckDB. Capabilities are advertised by presence
   (`supports_binned`, `supports_log2`), never probed by type.
3. **One source of truth per concept.** Filter semantics exist once in
   R (`make_mask`) and once in SQL (`value_predicate`), and the test
   suite proves the two agree. Within each side there is no second
   copy: every SQL predicate shape is generated by one function; every
   histogram count is produced by one function per mode.
4. **The parent app's interface is reactives out, one function in.**
   Out: `mask/rows/n_selected/selected_vars/filters`. In:
   `add_vars()`. Nothing else crosses the boundary.
5. **Elegance = deletion.** When two code paths drift toward each
   other (as the vector and aggregate render paths did), merge them
   behind the smallest abstraction that fits — here, "a counts
   provider".

## Layers and files

```
apps/*            demo + integration apps (self-contained on purpose)
   │  uses thanosUI/thanosServer + a backend, consumes rows()
R/thanos_module.R the reactive shell: widgets, observers, lifecycle
   │  calls pure helpers, talks to the backend contract
R/thanos_plot.R   pure: make_mask, bin_column, bin_counts,
   │              bin_spec_from_info, display_range, plot_histo*(engine)
R/thanos_columns.R pure: shared column coercion + statistics
   │              (used by backend_memory AND the db build scripts,
   │               so both data paths agree BY CONSTRUCTION)
R/thanos_backend.R        the contract + backend_memory
R/thanos_backend_sqlite.R backend_dbi (SQL generation, aggregation,
   │                      caching) + sqlite/duckdb wrappers
R/thanos_theme.R  visual identity (compact theme, plasma pair)
R/thanos.R        loader: private namespace, public API only
```

`db/` build scripts create the tall/skinny schema; `bench/` scripts
measure (sourcing `bench/bench_common.R` for shared timing helpers);
`tests/` are plain Rscript checks plus `snapshot-equivalence.R`, a
capture/compare harness that freezes the behavior of every layer.

## Key data shapes (the module's lingua franca)

- **filters**: `list(var = list(is_numeric, val, include_na))` where
  `val` is `NULL` (no filter), a numeric range possibly containing
  `±Inf` (slider endpoint = unbounded), or a character vector
  (categorical levels — or discrete-numeric membership when
  `is_numeric` is TRUE). `normalize_filters()` canonicalizes by
  dropping entries that impose no restriction; everything downstream
  (SQL, cache keys) sees only canonical state.
- **bin spec**: `kind = "num"` (origin/binwidth/mids/width/nbins,
  optional `log2p1`) or `kind = "cat"` (labels/nbins); produced by
  `bin_column()` (with row indices, vector mode) or
  `bin_spec_from_info()` (metadata only, aggregate mode). The two
  produce the same geometry for the same column.
- **counts**: `list(shown, sel, n_shown, n_sel)` — per-bin counts of
  rows passing all *other* filters, the subset also passing this
  variable's own filter, and the two row totals for the title.
  Produced by `bin_counts()` (vector mode: tabulate over cached
  indices) or assembled from `get_binned_pair()` + counts (aggregate
  mode). `plot_histo_counts(spec, counts…, engine)` renders either.

## The reactive graph (thanosServer)

```
input$filter_v ─debounce─▶ per-var observer ──▶ maskStore[v] (vector)
                                    └─────────▶ filterState (both modes)
input$vars ──▶ diff observer ──▶ add_var/remove_var (insertUI/removeUI,
                                  one state object per var in cache$var)
maskStore ──▶ looMasks (prefix/suffix cumulative ANDs, O(3k))
filterState ─▶ filtersNow (normalized canonical filter list)
looMasks / filtersNow ──▶ counts_for(v) ──▶ renderPlot (registered once
                                             per var, one body, engine-
                                             dispatched)
looMasks / filtersNow ──▶ globalMask ─▶ rows()/n_selected() accessors
```

Mode differences are contained in exactly two closures chosen at
server start: `counts_for()` (where do histogram counts come from) and
the mask/count accessors. Everything else — widgets, observers,
lifecycle, rendering — is one shared code path.

Per-variable lifecycle state lives in **one object**
(`cache$var[[v]]`: info, widget kind, bin, cached column, slider
bounds, observers, flags), created whole by `add_var()` and deleted
whole by `remove_var()` — not in parallel per-field lists.

## SQL generation (backend_dbi)

`value_predicate(f)` is the single translator from a filter entry to
SQL conditions on the value column: it returns `pass` (condition a
value must meet) and `fail` (condition marking a value as failing),
handling ranges with infinite bounds, discrete-numeric membership, and
categorical sets. On top of it:

- `filter_clauses()` wraps predicates in the NA-by-absence row_id
  algebra (`include_na = TRUE` → `row_id NOT IN (failing rows)`;
  `FALSE` → `row_id IN (passing rows)`).
- `get_binned_pair()` uses `pass` directly as the CASE condition for
  the sel column of the combined histogram query.
- `get_binned()` is a one-line delegation to `get_binned_pair(own =
  NULL)$shown` — it has no query logic of its own.

Caching (columns for the backend's lifetime; a bounded memo over
aggregate results, keyed by canonical arguments) and read-only
connections are backend concerns invisible to the module.

## What the consolidation pass removed

| redundancy | resolution |
|---|---|
| `get_binned` re-implemented `get_binned_pair`'s grouping SQL | delegated (≈35 lines gone, one memo path) |
| value-predicate SQL written 3× (two clause branches + own_pred) | one `value_predicate()` |
| tabulation logic in module renderPlot AND `plot_histo` | one `bin_counts()` used by both |
| engine dispatch closure rebuilt per variable + two public plot fns | `plot_histo_counts(…, engine)` dispatches; base impl unchanged |
| two near-identical renderPlot bodies (vector/aggregate) | one body + per-mode `counts_for()` |
| seven parallel per-var cache lists | one state object per var |
| column coercion + stats duplicated in backend_memory and the flights build script | shared `R/thanos_columns.R` |
| `timeit()` redefined in five bench scripts | `bench/bench_common.R` |

## Deliberate non-goals

- **Apps stay self-contained** (each carries its own loader stanza):
  they are copy-paste starting points, and DRYing them would couple
  the teaching examples to repo layout.
- **`db/build_big_sqlite.R` keeps its own streaming accumulator**: it
  computes stats incrementally over chunks (bounded samples for
  quantiles) and cannot reuse the whole-column helpers without
  holding 38M-row columns in memory. The duckdb build computes stats
  in SQL for the same reason.
- **No R package yet**: the loader provides the namespace benefit
  without changing `source()`-based usage (Project.md constraint).
  The file layout is already package-shaped if that changes.

## Verification methodology

`tests/snapshot-equivalence.R` captures, on fixed seeds: every pure
helper's output; every backend function's output on a 500-row fixture
(memory, SQLite, DuckDB); three whole-module scripted interaction
sequences (vector×2 backends, aggregate) recording mask/rows/counts/
filters after each step; the built data of the ggplot engine and the
PNG bytes of the base engine. A snapshot captured before this
consolidation compares EQUIVALENT after it, alongside the ~125-check
functional suite. Any future refactor should follow the same recipe:
capture, change, compare.
